I. The System at a Glance

1.1. What is this platform about

The Derivatives Portfolio Pricer (DPP) is an open-source, full-stack derivatives portfolio valuation platform deployed entirely in the cloud and designed for buy-side valuation workflows. It combines a browser user interface (UI), a pricing API, a relational database, an automated market-data pipeline, and an AI assistant that can operate it on request. Its goal is to manage instruments and trades using front-office-grade processes and controls in order to value the portfolio with a Monte Carlo engine that returns both prices and risk metrics.

Every step of that workflow can be performed by hand in the screens, or requested in plain language to Carlo, the AI assistant embedded in the platform.

For more technical information, please visit the GitHub repository Derivatives-Portfolio-Pricer.

1.2. What the platform does

The workflow mirrors how valuation is handled by practitioners. The first step is to define the market inputs; at the minimum, that includes underlyings with historical prices and interest rate curves. The second step is to define the instruments, link them to underlyings, and create trades with quantities and dates. Finally, the valuation engine uses those inputs to return prices and risk metrics for each trade, allowing an aggregated computation at the portfolio level.

The platform supports classical and exotic derivatives (European, Asian, digital, barrier, lookback, and range options). The core outputs are driven by a multi-method Monte Carlo engine, and are the following:

  • Price & Standard Error. These are the theoretical value and estimation error of each trade.
  • Risk Metrics, such as Delta, Gamma, Vega, Theta, and Rho.

1.3. Architecture Overview

The most effective way to understand the DPP architecture is thinking of it as three connected “flows”: the “interactive valuation,” the “assisted valuation,” and the “daily data ingestion.”

Interactive valuation flow

This is what the user experiences in the browser. The DPP website is served by a software called “Nginx”, which hosts the UI files and routes any action (like adding instruments, saving trades, etc.) to the API service. The API then reads from and writes to the Postgres database, and it executes the pricing logic when the user requests a valuation.

Assisted valuation flow

This is the same workflow held as a conversation. A question typed to Carlo travels to a small service that attaches the platform’s instructions and tools, and forwards it to a language model (Claude Sonnet 4.6, served by Amazon Bedrock). Whenever the model needs data or a calculation, the browser executes that step against the same API used by the screens; i.e., the assistant sees and does exactly what a user in front of the screen would.

Daily ingestion flow

This is what keeps the system current. We use an Amazon Web Service (AWS) called EventBridge, which triggers a scheduled “job” (AWS Lambda) after each trading day. That job pulls market data for our predefined underlyings and yield curves from external sources, pushes a cleaned version of the data into the API so the database stays up to date, and writes raw snapshots into a centralized cloud storage (S3). Other AWS tools involved are Glue crawlers, which catalog the S3 snapshots and their partitions, and Athena, which queries the history using SQL for audits, backfills, and quality checks.

1.4. What makes this platform “production-style”

The intention of this platform is not to be a regular pricing option tool (which, indeed, is not the hard part). Instead, it’s designed as an operating system that is able to perform a specific task reliably at a production level. In this case, we implemented a valuation task, but the same system layout can be applied for many other financial tasks (budgeting, risk management, etc.).

In that sense, this platform deliberately prioritizes the efficiency, operability and security of the system by:

  • Defining a static and fast UI.
  • Building a hidden transactional “shadow” API.
  • Utilizing Postgres as the “source of truth” for the app.
  • Implementing a data lake (S3) as the append-only historical store for raw data.
  • Reserving every change of the data to the owner, while reading and pricing remain open to any visitor.
  • Giving the AI assistant the same doors as a regular user, and no others.

1.5. How security is handled by DPP

In DPP, only the web ports are public, while the API, the database and the assistant’s service are kept private behind Nginx and localhost routing. In that sense, there are three types of callers, and each one holds exactly the access it needs:

Visitor

Reads every screen, prices “what-if” contracts, runs valuations, and asks Carlo. This is open by design, since none of these actions modifies the stored data.

Owner

Adds, edits and deletes underlyings, derivatives, trades and curves, from the screens or through Carlo. A passcode unlocks a signed token that lasts eight hours, and Nginx verifies it on every request that changes data.

Nightly job

Loads prices and rate points. Thus, regular ingestion uses an authenticated API key header rather than exposing database credentials outside the host.

Notice that the passcode is stored only as a salted hash, and that the language model is reached with the server’s own AWS role, so there is no model key to protect. This is a common practice among internal systems designed to keep the public surface area small, concentrate trust in a single entry point, and make control points explicit (authentication, logging, and permission boundaries).

1.6. The layers of the platform

Hence, we can summarize the production-style architecture in 8 layers:

Front door

Nginx serves the DPP UI at https://derivativespricer.com/. That URL returns the static UI files, and any request under /api/ is then forwarded to the internal services running locally on the same EC2 host.

User interface

A React application organized as a workstation, with charts for the market data, grids and tickets for instruments and trades, and a valuation screen.

Application layer

API endpoints manage underlyings, options, trades, curves, and valuation.

Database layer

Postgres stores entities and time series (prices, rate points) used for valuation.

Pricing layer

Monte Carlo engine supports multi-method configurations, such as variance-reduction, low-discrepancy sequences and/or multi-threaded execution.

AI assistant

Carlo reads the book, prices “what-if” contracts, runs valuations and, for the owner, records changes.

Data engineering layer

Scheduled ingestion + S3 raw snapshots + Glue Catalog + Athena SQL.

Observability

CloudWatch centralizes logs, metrics and alarms across the stack.

Each layer will be discussed in further sections.

II. Layer 1: Front Door

2.1. What “Front Door” means in DPP

In DPP, the front door is the only public entry point of the platform. It receives a browser request, decides whether the request is asking for a static file (the UI) or an application action (an API call), and then routes it safely to the correct internal component. In other words, this layer is the perimeter that defines what the internet can and cannot touch.

We implemented this with Nginx since it is a mature and production‑standard web server for hosting static sites and acting as a reverse proxy. That dual role matters here. The UI should be fast and cacheable, while the API should be reachable only through a controlled gateway that can enforce consistent routing and keep the public surface area small.

2.2. How the front door keeps the platform fast

The front door also defines how fast the platform feels. The JavaScript and CSS files carry a fingerprint of their content in their names; thus, the browser can keep them for a year, while the pages that reference them are always revalidated. In that sense, a release reaches every visitor on the next page load, with no stale copies in between.

In addition, the API responses and the text assets travel compressed (gzip). That matters most for the largest download of the application, the price history of every underlying, which travels at roughly one seventh of its size.

2.3. How traffic is routed

A practical way to understand the routing is that DPP has four “types” of HTTP requests, and Nginx handles each one deterministically:

Static asset requests

The browser asks for HTML, CSS, JavaScript, fonts and images. These are returned directly as files, with no application logic involved.

Application requests

The browser reads data, prices a contract, or requests a valuation. In the UI, these actions are implemented as calls under /api/, which Nginx forwards to the internal API service.

Change requests

The browser creates, edits or deletes a record (a trade, a curve, etc.). Before forwarding it, Nginx verifies that the request carries a valid owner token; otherwise, the request is answered with a “locked” message and never reaches the API.

Assistant requests

The conversation with Carlo travels under /api/ai/ to the assistant’s service, and the answer is streamed back without buffering, so the text appears as it is written.

Reverse proxy boundary: none of the internal services is exposed directly to the public internet. Each one listens on the host only, and Nginx is the single way in.

This split is deliberate. Applications usually load a lightweight UI once, and then the browser makes small, explicit API calls as needed. That is a common pattern in internal trading and risk tools because it keeps the UI responsive while preserving a clean transactional boundary on the server side.

2.4. Why this layer is a control point

The most important design decision is that only web traffic is public. Internal services are treated as private components and are reachable only through the application’s routing rules. This keeps secrets and write access paths out of the public network path. In that sense, the system is easier to reason about: if something is reachable from the internet, it is reachable through one door, under one hostname, with one routing policy.

From an operability perspective, this also accelerates debugging. For instance, if the UI loads but API actions fail, the problem is downstream in the application tier. If the UI itself does not load, the issue is at the web server level (deployment, routing, or static assets). That separation reduces the scope of failure and makes outages more diagnosable.

III. Layer 2: User Interface

3.1. A workstation rather than a form

The UI is organized the way a trading workstation is. A fixed panel on the left tells users where they are; the center holds the data; and a mirrored panel on the right holds what users can do there (the ticket or the settings of that section). In that sense, the layout answers three questions at a glance: where am I, what am I looking at, and what can I do about it.

Notice that the UI is read-only by default. Every ticket shows a lock line; i.e., until the owner unlocks the platform with the passcode, the buttons that save or delete stay off, while the buttons that price remain available to anyone. Likewise, the predefined underlyings and the Treasury curves cannot be edited from the screens, since they belong to the nightly ingestion.

The colors are part of the design as well. Teal marks what is positive or bought, and orange marks what is negative or sold. We preferred that pair over the usual green and red because it remains readable for color-blind users.

3.2. What each screen shows

ScreenWhat it shows
UnderlyingsThe price chart of the selected stock, with the strikes of its open derivatives and its trades marked on it, plus a watchlist with a 26-week sparkline per stock
DerivativesA dense grid of contracts filtered by option type, with the ticket to define a contract on the right
TradesThe blotter with premium, market value and profit or loss per trade, and a ticket that can take its price from the engine
RatesThe curve chart with other curves overlaid on it, the key tenors month by month, and the points of the selected curve

Carlo AIThe conversation with the assistant in full view; the same conversation is one click away from every other screen

3.3. How the UI is built

The UI is a React application written in TypeScript and bundled with Vite into static files, which is exactly what makes it fast to serve and easy to cache. We deliberately avoided external component kits and chart libraries; i.e., every chart is drawn directly as SVG by the application itself. The practical advantage is a small download (roughly 100 KB of compressed JavaScript) and a consistent look across screens. In addition, the typefaces (IBM Plex) are served by the site itself, so the page does not depend on any third party to render.

The result is a single set of static files that is served to every visitor. In addition, each screen has its own address (for instance, #/trades), so a link can point directly to a specific screen.

3.4. How the UI loads and stays consistent

On opening, the UI requests derivatives, trades and curves at once, and leaves the price history (the largest download) for last, so the screens are usable before the charts are complete. Then it values the whole book once, as of now, and every screen reads from that same run: the unit values in Derivatives, the market value and the profit or loss in Trades, and the bars and Greeks in Valuation. Thus, two screens never disagree about the same position.

The same principle applies after a change. The lists that depend on each other are reloaded together, and a newer valuation always replaces an older one. Finally, deleting asks for confirmation inside the ticket itself, which keeps destructive actions explicit.

IV. Layer 3: Application Layer

4.1. The API as the platform’s transactional “shadow”

The application layer is where DPP stops being a static website and becomes a system. The browser UI is intentionally lightweight; i.e., every meaningful action the user takes (creating an underlying, defining an option contract, saving a trade, updating a curve, or running a valuation) becomes an API request that is validated, persisted, and executed server‑side.

This is exactly how production tools are typically structured. The UI should be fast and user‑friendly, but the “truth” must live behind a transactional boundary, where inputs can be validated consistently and where results can be reproduced later from stored records.

4.2. What the API is responsible for

We think of the API as having two jobs. The first is portfolio and market‑data management: it enforces the relationships between objects (an option references a valid underlying; a trade references a valid instrument; a curve contains coherent rate points). The second job is valuation orchestration: it reads the current portfolio state and market inputs from the database, calls the pricing engine with the selected simulation settings, and returns structured results back to the UI.

The practical advantage is consistency. The API is the only write path to the database, so the system can enforce the same validation rules regardless of whether the request originated from a browser click, from the assistant, or from the automated ingestion pipeline.

4.3. The endpoints of the API

As a general outline, the API exposes one group of endpoints per object of the workflow:

GroupRouteWhat it does
Underlyings/api/UnderlyingsStocks and their daily closes, including the bulk upsert of prices by symbol used by the nightly job
Derivatives/api/OptionEntitiesOption contracts of the six supported types, each one with its own fields (rebate, barrier level, and barrier type)
Trades/api/TradesBuys and sells of an instrument, with quantity, trade date and price
Rate curves/api/RateCurvesCurves and their rate points, including the full replacement of points used by the nightly job
Valuation/api/ValuationPrices a set of trades under the chosen simulation settings, as of now or as of a past date
Single pricing/api/Simulation/price-optionPrices one contract that is not stored, which is what makes “what-if” questions possible

4.4. Swagger as an explicit contract surface

For transparency and testability, the API describes each endpoint through the OpenAPI standard, and Swagger renders that description as interactive documentation. Each endpoint has a defined request/response shape, which makes the platform auditable and reduces the “black box” problem that often exists in financial tooling. Notice that Swagger is served by the API inside the host, for whoever operates the server; it is not published through the front door.

4.5. What a valuation request carries, and what it returns

A valuation request names the trades to value, the rate curve, and the simulation settings (number of paths and time steps, antithetic paths, control variate, low‑discrepancy sequence, and multi‑threading). Optionally, it also carries a valuation date. In that case, the API uses only the closing prices on or before that date, counts the time to expiry from it, and leaves out the trades executed afterwards; i.e., the book is valued as it stood on that day.

In return, each trade comes back with a status (valued, expired, or not traded yet), its quantity, unit price and position value, the spot price used and its date, the time to maturity, the standard error, and the Greeks. Thus, an expired option returns zero with an explicit status instead of a misleading number. Similarly, the list of derivatives is deliberately light: it returns the contract terms and a short reference to the underlying, rather than the full price history attached to it.

4.6. A typical valuation lifecycle

An example of a valuation cycle across the platform can be summarized in 4 steps:

  • Define market inputs: user creates or selects underlyings with historical prices, and selects an interest rate curve.
  • Define instruments: user creates option contracts linked to the chosen underlyings, including strike and expiration details.
  • Create trades: user records positions with quantities and trade dates, which makes valuation portfolio‑aware rather than “one‑off.”
  • Run valuation: user submits simulation settings and selected trades; the API runs pricing and returns prices plus risk metrics.

The key point is that this lifecycle is stateful; i.e., the API persists the objects so valuation is reproducible, and it returns results in a way that supports aggregation at the portfolio level. That is the difference between a simple calculator and an operating platform.

V. Layer 4: Database Layer

5.1. Postgres as the system’s “source of truth”

The database layer is what makes DPP reliable and repeatable. In a valuation workflow, the hardest operational problem is not computing a price once; it is ensuring that users can reproduce a valuation later using the same portfolio state and the same market inputs. DPP addresses that by using Postgres as the persistent store for both “portfolio objects” and the time series that drive pricing.

Importantly, the database is treated as a private component. The UI never talks to Postgres directly, and neither the assistant nor the ingestion pipeline bypasses the API. All writes flow through one controlled path, which keeps schema rules, validation logic, and permission boundaries centralized.

In practice, the database is PostgreSQL 16 running in its own container with a persistent volume, and its schema is defined and versioned by the API through Entity Framework Core migrations.

5.2. Operational state versus historical archive

In the interactive flow, Postgres holds the operational state the application needs to function quickly. In parallel, the raw historical snapshots live in the data lake (S3). In that sense, Postgres is optimized for “what the system needs right now,” while the data lake is optimized for “what the system has ever seen,” which is critical for audits and backfills.

5.3. What is stored and why

At a high level, the schema has two connected domains: (1) portfolio objects that define what is held, and (2) market inputs that define how those holdings should be valued. The following summary reflects the intent of the model rather than an exhaustive listing of every column:

DomainWhat it representsWhy it matters
InstrumentsUnderlyings plus option contracts (classical and exotic)Preserves contract terms so trades can be re‑valued consistently
TradesPositions that reference an instrument with quantity and datesMakes valuation portfolio‑aware rather than “one‑off” pricing
Historical pricesTime series linked to an underlyingSupports volatility estimates and scenario generation
Rate curvesA curve header plus rate points across maturitiesEnables discounting and rate sensitivity measurement

Under the hood, the model relies on basic relational guarantees: trades must reference a valid instrument, historical price rows must reference a valid underlying, and curve points must reference a valid curve. Those constraints may sound mundane, but they are exactly what prevents “silent data corruption” in practice. Thus, if a dependency is missing, the system fails loudly instead of producing a misleading valuation. In that sense, the database is the integrity layer that turns the platform into a controllable system and keeps the UI simple.

A subtle but important design choice is how option contracts are represented. DPP keeps common option parameters centralized while allowing contract‑specific fields (barriers, averaging windows, lookback logic, digitals, and range constraints) to live in structured extensions. This preserves clarity and makes it straightforward to add new exotic features without turning the schema into one oversized table.

VI. Layer 5: Pricing Layer

6.1. What the pricing layer does (and what it intentionally does not do)

The pricing layer is the computational core of DPP. Its job is to take a well‑defined contract, a well‑defined set of market inputs, and a well‑defined simulation configuration, and then produce a valuation result that is both interpretable and reproducible. In practice, that means a Monte Carlo engine that generates price paths, maps them into payoffs, discounts them, and aggregates them into a price estimate with an explicit measure of uncertainty.

What this layer intentionally does not do is “guess” the portfolio state. The portfolio (trades and instruments) and market inputs (prices and curves) are retrieved from the database through the API. This separation keeps the engine focused on the mathematics, while the application layer remains responsible for validation, persistence, and orchestration.

6.2. How the simulation is executed

Conceptually, every valuation run follows a repeatable sequence: generate random shocks, evolve the underlying price through time, compute the payoff at maturity (or along the path for path‑dependent contracts), discount the payoff back to today, and then average across paths. The same run also produces a standard error, which is a practical diagnostic: it tells the user whether the number of paths should be increased, or whether the estimate is already stable.

The market inputs of each run come from the stored data. The price of the underlying evolves as a geometric Brownian motion; its volatility is estimated from the stock’s own history (the standard deviation of the daily log returns, annualized with 252 trading days), and the interest rate is read from the selected curve at the tenor nearest to the remaining life of the contract.

6.3. The contracts the engine prices

Because the platform supports multiple option styles, the payoff logic is modular. Thus, a European payoff depends only on the terminal price, while an Asian or lookback payoff depends on the full path:

ContractWhat the payoff depends on
EuropeanThe price at expiry against the strike
AsianThe geometric average of the path against the strike
DigitalA fixed amount, paid only if the contract expires in the money
BarrierThe price at expiry, as long as the path touched (knock‑in) or never touched (knock‑out) the barrier, from above or from below
LookbackThe maximum of the path (call) or its minimum (put) against the strike
RangeThe distance between the maximum and the minimum of the path

6.4. The methods embedded in the engine

DPP’s implementation supports practical Monte Carlo enhancements that are common in production settings. These include antithetic sampling, a delta‑based control variate, optional low‑discrepancy sequences (Van der Corput), and parallel execution across the processor’s cores to accelerate runtime. The objective is not to overwhelm the user with theory; it is to expose the knobs that matter when users have to balance accuracy, stability, and compute cost.

Notice that barrier and digital contracts introduce discontinuities, which is exactly where variance reduction and better sampling can materially improve stability.

The Greeks follow the same logic. Each sensitivity is obtained by revaluing the contract after a small bump of one input (spot, volatility, time, or rate) over the same random numbers of the base run. In that sense, the difference between both valuations reflects the bump itself and not the simulation noise.

6.5. The outputs the platform returns

As a general outline, the platform returns the following information:

Price & Standard Error

The estimated fair value and the Monte Carlo estimation error. This tells not only “the price,” but also “how stable the estimate is.”

Greeks (risk metrics)

Trade‑level sensitivities such as Delta, Gamma, Vega, Theta, and Rho. These are essential for interpreting valuation changes under market moves.

Portfolio aggregation

Once each selected trade is valued, the system can aggregate results into a portfolio‑level view, which is the natural end goal in buy‑side valuation workflows.

In that sense, pricing in DPP is a callable service inside a system, with persisted inputs and structured outputs. That is what makes the platform “production‑style”: the engine is operationally embedded and fully available for users.

VII. Layer 6: AI Assistant

7.1. What Carlo is

Carlo is the AI assistant embedded in DPP, and its name comes from Monte Carlo, the method that the engine prices with. It reads the book, prices “what-if” contracts, runs valuations as of today or as of a past date on any curve, brings up the screen it is talking about and, for the owner, records changes. In other words, the workflow of the screens is also available as a conversation.

What Carlo intentionally does not do is give investment advice. It explains and computes over a demonstration portfolio, and it stays within the platform: its data, its pricing logic, and the option theory needed to read its results.

7.2. Reading for everyone, changes for the owner

For a visitor, the model only receives the tools that read and compute. The tools that add, edit or delete are offered only when the request carries a valid owner token and, even then, each change is displayed as a card that must be confirmed before it is applied.

In addition, the front door applies the same owner check to the API itself. In that sense, the rule holds regardless of the path a request takes: a screen, the assistant, or a direct call to the API.

7.3. How a question is answered

As a general outline, each question follows the same sequence:

  1. Request: the browser sends the conversation to the assistant’s service, a small Node.js program that runs on the same host.
  2. Context: the service attaches the platform’s instructions and the list of tools, verifies the usage limits, and calls the language model (Claude Sonnet 4.6) through Amazon Bedrock.
  3. Tool use: the model either answers in text or asks for a tool; e.g., “value the NVDA trades on this curve.”
  4. Execution: the tool runs in the browser, with the same API calls and the same data used by the screens, and its result goes back to the model.
  5. Answer: the reply is streamed to the panel as it is written, and each step is displayed while it runs.

The key point is the fourth step. The assistant’s service has no route to the pricing API or to the database; i.e., whatever Carlo does, it does through the user’s own browser session and under the user’s own permissions. Thus, the assistant cannot reach anything that a person in front of the screen could not reach.

7.4. Answers that respect the numbers

A Monte Carlo figure always carries noise, and an assistant that ignores it can sound confident while being wrong. For that reason, the valuation tool returns the totals of the position with their standard error, together with the position Greeks expressed in plain units (per volatility point, per calendar day, and per 100 basis points of rates).

Carlo is instructed to answer any sensitivity question from the Greeks of a single run rather than from the difference between two runs, and to say it plainly when a difference is too small to be told apart from noise.

7.5. Limits and privacy

Since the assistant is open to any visitor, its use is bounded. There are rate limits per visitor and for the site as a whole, plus a daily and a monthly spending cap; once a cap is reached, Carlo rests until the next day or month, and says so.

Regarding privacy, the service logs sizes, token counts and cost, but never the text of a conversation, and no conversation is stored on the server.

VIII. Layer 7: Data Engineering Layer

8.1. Why a data engineering layer exists in a valuation system

A valuation engine is only as good as the inputs it consumes. If market data becomes stale, the system becomes misleading even if the model is mathematically correct. For that reason, DPP includes a dedicated data engineering layer that refreshes predefined market inputs on a schedule and keeps an auditable history of what was ingested and when.

Notice that the overall goal is not “big data”, but operational continuity; i.e., the platform should be usable on any day without manual data loading, while still retaining the ability to trace and audit the snapshots that supported a given valuation.

8.2. The ingestion workflow, end to end

As a general outline, the ingestion workflow can be summarized in the following steps:

Schedule

An AWS EventBridge rule runs the job at 03:30 UTC from Tuesday to Saturday (i.e., after each trading day in the US), making the cadence deterministic and inspectable. If a run cannot be delivered, it is retried and then parked in a dead‑letter queue.

Extraction + normalization

An AWS Lambda job, packaged as a container image, pulls the daily closes of the 50 predefined underlyings from Yahoo Finance and the Treasury and SOFR rates from FRED (12 series, from overnight to 30 years), and normalizes them into a consistent schema.

Operational upsert

The job pushes every trading day of its window into the DPP API, so Postgres reflects the current operational state used by the UI and the pricing engine. The upsert is idempotent per symbol and date; thus, sending the same day twice is harmless.

Raw persistence

Each run writes “append‑only” raw snapshots into S3 (one partition per trading day), together with a manifest‑style record that captures “what was produced.”

8.3. Why S3 + Glue + Athena are included

In the current configuration, S3 stores raw snapshots as partitioned files using a dt=YYYY-MM-DD convention. Equity price extracts are written under raw/prices_ndx50/, and rate series extracts are written under raw/rates_fred/, with filenames that include a UTC run identifier so each execution produces a unique, append-only artifact.

Each run also writes a lightweight manifest under raw/manifests/. The manifest records the run identifier, the window covered, the “as-of” dates used for prices and rates, row counts sent to the API, the curve names updated, any split detected, and the exact S3 keys produced in that run. Glue crawlers catalog these prefixes and recognize the dt= partitions, which keeps Athena queries stable and efficient. In particular, in Athena, partition pruning can filter by snapshot date, and the manifest table can be joined back to the snapshot tables to reconstruct the precise market inputs generated by a specific ingestion run.

This design also keeps concerns separated: the application database stays lean and focused on operational needs, while the data lake retains the full ingestion lineage. That is the same separation seen in production analytics stacks, even when the underlying dataset is small (like, arguably, in this case).

8.4. Reliability and auditability details

In practice, ingestion has to be resilient to real‑world data issues: intermittent upstream outages, throttling, and partial responses. That is why the job is designed around repeatable runs, retries, and clear “what happened” artifacts.

In particular, the job is able to heal itself. Its window widens automatically back to the last day archived in the data lake; thus, a missed night (or even a long outage) is recovered by the next run without manual work. Likewise, when the source reports a stock split inside the window, the job pulls the full history of that symbol again, so the stored prices stay on a single share basis and the volatility estimate is not distorted. The same job also accepts manual runs: a dry run that validates without writing, a backfill between two dates, or a correction for specific symbols.

Mainly, the manifest records act as the bridge between the operational system (Postgres) and the historical archive (S3). In that sense, we can always point to a specific run and see what datasets were produced, instead of treating the data lake as an opaque folder.

Over time, this becomes a governance tool. If a valuation is questioned, we can trace the market snapshot that supported it. Similarly, if a backfill is required, Athena can query historical partitions without touching the operational database. In that sense, the data engineering layer is both a refresh mechanism and an audit mechanism.

IX. Layer 8: Observability

9.1. Observability as an operational requirement

Observability is what makes DPP operable day to day. In a valuation platform, a silent failure is worse than an obvious one: if a scheduled ingestion does not run or if an application regression is introduced, the system can drift without the user noticing. For that reason, we treat observability as a first‑class layer rather than an afterthought.

9.2. The three questions this layer must answer

Did the ingestion run successfully?

This is the minimum requirement for keeping predefined underlyings and curves current, and it is also the fastest signal that “today’s state” is trustworthy.

If something failed, where did it fail?

Logs must be searchable and timestamped so a failure can be tied to a specific run, not guessed from symptoms.

Is the platform behaving normally over time?

Error counts, latency patterns, and runtime duration should make anomalies visible even when the UI still appears healthy.

9.3. What signals are captured

DPP produces operational signals at each boundary. At the edge, web server logs capture request volume and failures. In the application tier, API logs capture validation failures and runtime exceptions. In the ingestion tier, each scheduled run emits a structured timeline that can be tied back to the artifacts written into the data lake. None of these streams are useful in isolation; the value comes from having them centralized so we can reconstruct the sequence of events across layers.

In CloudWatch, that means four log groups (web server access, web server errors, API, and ingestion), each one retained for 14 days, a dashboard that follows the CPU and network activity of the host, and the following alarms, which notify by email through SNS:

AlarmWhat it catches
No ingestion run in the last 80 hoursA schedule that silently stopped (the window is wide enough to cover a weekend)
An ingestion run ended in errorA failed extraction, upsert or archive
An ingestion run lasted more than two minutesA source that is slowing down or throttling
A message arrived in the dead‑letter queueA scheduled run that could not be delivered
High CPU on the hostA valuation load or a process that is saturating the server

9.4. How we structure monitoring in practice

DPP centralizes logs from the ingestion runtime, the web server edge, and the API runtime, which provides a coherent timeline of system behavior. In addition, basic metrics (invocations, errors, and duration) allow for alarms when something deviates from the expected pattern. The objective is to reduce “time to diagnosis”: when something breaks, the system should reveal the problem quickly and with enough context to fix it.

From the user’s perspective, this shows up as predictability and faster fixes. If ingestion fails, it is visible immediately and can be corrected before it affects the next valuation. If the API begins returning errors, the logs can be traced to the exact endpoint and request path involved. In fact, the left panel of every screen displays the date of the latest close and whether the nightly update is on schedule. In that sense, observability is not “extra”; it is the mechanism that makes the platform trustworthy as an operating system rather than a fragile demo.

Finally, this layer closes the loop with security. When the public surface area is intentionally small, logs become the audit trail that proves the boundary is working. Over time, that auditability is what enables stricter controls (user roles, change tracking) without losing the ability to diagnose issues quickly.

X. Further Improvements

DPP is intentionally “small but complete.” At its core, it proves an end-to-end valuation workflow, and it proves the ability to operate that workflow on cloud infrastructure. The natural next step is to deepen governance and market realism without losing clarity. In that sense, DPP as a software has some natural extensions and improvements:

Separate the application and database residence

So far, the UI, the API, the assistant’s service and the database live in the same EC2 instance. This is sensible for an implementation of this size, since it saves resources (AWS credits); however, a more well-designed infrastructure involves the use of separate instances.

Richer market models

This is more a theoretical/academic improvement. In practice, we could add volatility surfaces, stochastic volatility, and calibration workflows to improve the overall user experience and the deliverable pricing product.

User access controls

So far, a single owner passcode separates reading from changing. This could be extended by adding named users and role-based permissions, so different users (or teams) see only the portfolios, trades, and market inputs they are allowed to manage, with changes tracked per user.

Reproducible simulations

A fixed random seed per valuation would make two runs directly comparable, which matters when the question is the effect of a scenario rather than the level of a price.

In that sense, the project is both a valuation tool and a financial database & software architecture. It connects instrument mechanics, data engineering, an AI assistant, and cloud deployment into one coherent system that, at least in this implementation, is completely open source.
